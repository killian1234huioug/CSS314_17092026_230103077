## Phase 1: Forensic Diagnosis of False Sharing & Cache-Line Contention

### 1.1 Experimental Setup

The experiment was performed on an Apple M3 processor with 8 physical cores and 8 logical threads. Python multiprocessing and shared memory were used to investigate false sharing.

Each process updated its own 64-bit integer in a shared memory buffer. Different stride values were tested to change the distance between memory locations.

The experiment used:
- Total operations: 24,000,000
- Process counts: 1, 2, 4, and 8
- Stride values: 1, 2, 4, 8, 16, and 32
- Warm-up runs: 2
- Timed runs: 7

### 1.2 Cache-Line Contention Experiment

The first experiment used 8 processes and compared different stride values.

| Stride | Separation (Bytes) | Median Time (ms) | IQR (ms) | Throughput (Mops/s) |
|---:|---:|---:|---:|---:|
| 1 | 8 | 643.83 | 36.56 | 37.277 |
| 2 | 16 | 640.21 | 19.54 | 37.488 |
| 4 | 32 | 622.24 | 21.99 | 38.571 |
| 8 | 64 | 607.99 | 6.10 | 39.474 |
| 16 | 128 | 605.60 | 53.16 | 39.630 |
| 32 | 256 | 606.34 | 28.52 | 39.581 |

The results show that execution time generally decreases when the distance between process data increases. The fastest result was obtained with stride = 16, which provides 128 bytes of separation.

The median execution time decreased from 643.83 ms to 605.60 ms. This represents an improvement of approximately 5.94%.

However, there was no sharp performance change at one exact stride value. Therefore, the experiment does not conclusively identify the cache-line boundary.

### 1.3 Karp-Flatt Analysis

The second experiment compared parallel performance using stride = 1 and stride = 16.

**Stride = 1**

### 1.4 Forensic Analysis

When processes update adjacent memory locations, several values may occupy the same cache line. This can cause false sharing and additional cache-coherence traffic.

The results suggest that increasing the distance between process data reduces some of this overhead. The difference is especially visible when using 8 processes.

However, multiprocessing overhead, process scheduling, and other system factors may also affect the measurements. Therefore, false sharing is a possible explanation for the observed performance difference, but it cannot be confirmed as the only cause.

## Phase 4: Load Balancing

### 1. Experimental Setup

The experiment compared three scheduling strategies using 12,000 tasks and 8 parallel processes on an Apple M3 processor.

The workload was intentionally unbalanced. The computational cost of each task was defined as:

K(i) = 1 + floor((i / 60)^2)

This means that tasks with larger indices require more calculations.

Three scheduling strategies were tested:

1. Static Contiguous Scheduling.
2. Cyclic Round-Robin Scheduling.
3. Dynamic Scheduling using a shared counter.

For dynamic scheduling, six chunk sizes were tested: 1, 4, 16, 64, 256 and 1024. Each configuration was measured three times.

### 4. Best Dynamic Chunk Size

The best dynamic configuration was:

- Best chunk size: C* = 1
- Median wall time: 2.074022 seconds
- Load imbalance: 1.003046

A chunk size of 1 provided the most balanced distribution among the tested dynamic configurations.

However, smaller chunks require more frequent access to the shared counter. This introduces synchronization overhead.

### 5. Analysis and Comparison

Static Contiguous Scheduling had the worst performance, with a median execution time of 3.881669 seconds. The reason was the increasing computational cost of tasks with larger indices.

Cyclic Round-Robin improved performance significantly by distributing tasks from different parts of the workload among all workers. Its median execution time was 2.030769 seconds.

Dynamic Scheduling with C=1 achieved the lowest load imbalance, but it was slightly slower than Cyclic Round-Robin because of shared counter synchronization overhead.

Larger dynamic chunks reduced the frequency of synchronization, but they also increased workload imbalance. For example, C=1024 resulted in a load imbalance of 1.623226 and a median execution time of 2.979554 seconds.

Overall, Cyclic Round-Robin achieved the best execution time, while Dynamic Scheduling with C=1 achieved the best load balance among the tested dynamic configurations.
